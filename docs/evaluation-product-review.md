# 产品化评测设计：grilling 审查记录

日期：2026-10-19。状态：九项产品决策及 Q10 完整共同理解均已确认，完整方案已重写，运行代码尚未实施。用户要求以健壮、扩展、追踪、观测、对比、归因为完整产品验收目标，不接受以缩减范围的“首期方案”代替总体设计。以下缺口记录来自对当时 v2 及现有实现的审查；主文档已由[完整产品方案 v3](metric-evaluation-design.md)替代，不将设计完成当作运行验收通过。

## 已确认约束与决策

Pi 架构优先，不大改上游；SQLite 作为业务数据底座；当前决策模型为 DeepSeek；并发配置默认 5、上限 10，需明确它约束的资源和所有入口。

| 决策 | 用户确认结果 | 直接影响 |
| --- | --- | --- |
| Q1 部署 | 单机多进程，完整验证恢复与隔离 | 全局配额不能按进程倍增；不声称已支持跨机器调度 |
| Q2 资源竞争 | 在线优先，评测有最低份额，实验间公平，空闲额度可借用 | 禁止长期饥饿；借出的在途请求不抢占，在线并非零等待 |
| Q3 产品入口 | 工作台＋API/CLI，统一实验记录 | 创建、进度、暂停/取消/续跑、对照和裁定必须使用同一服务契约 |
| Q4 故障恢复 | 确定任务自动恢复，未知调用对账后显式续跑 | 不能静默重试未知请求；新尝试保留旧证据及可能费用 |
| Q5 发布职责 | 强制质量门，严重违规阻断 | 配置成为默认版本前需有可验证放行记录 |
| Q6 知识范围 | 结构化规则＋文档依据，按实测选择检索 | 规则负责计算，文档提供出处，候选检索不能改写权威口径 |
| Q7 数值可见边界 | 校验通过后发布数值，候选仅供工作台调试 | 发布绑定验证证据；已发布纠正显式保留版本 |
| Q8 追踪保留 | 全部完整产物保留至手动删除 | 不设置自动过期删除；存储不足应背压并提示，不静默丢证据 |
| Q9 发布取舍 | 以质量为主，耗时和费用只作提示 | 严重违规与质量条件决定发布；不将较慢或较贵单独设为拒绝发布条件 |
| Q10 共同理解 | “确认，按此重写完整产品方案” | 授权按以上完整范围重写契约、调用链和验收矩阵；本轮不修改运行代码 |

## 已核实的阻断性缺口

| 缺口 | 具体反例与代码证据 | 完整设计必须交代 |
| --- | --- | --- |
| 多进程配额未统一 | 每个 Application 各建池，不同 dataDir 的 PID 锁互不约束：[application.ts](../apps/medical-query/src/application.ts)、[runtime-lock.ts](../apps/medical-query/src/runtime-lock.ts) | 单一配额权威、所有模型/修复/judge/embedding 入口、真实在途与未知请求记账 |
| 实验公平与在线容量不足 | online 仅排队优先；5 个 eval 可先占满；共享队列可使在线收到 429：[runtime.ts](../apps/medical-query/src/runtime.ts) | 类别最低份额、实验与方案公平、队列容量、借用/归还规则、背压与饥饿测试 |
| 客户端退出不等于停止 | POST 已接受但响应丢失后，catch 结束该题而服务继续执行：[evaluate.ts](../apps/medical-query/src/evaluate.ts)、[l0-evaluate.ts](../apps/medical-query/src/l0-evaluate.ts) | 发送前持久化槽位/requestId、对账、暂停与取消区别、收尾及费用状态 |
| 缺完整实验恢复状态 | 当前整批写结果；业务 running 重启变 interrupted，queued 可恢复 | 实验/槽位/尝试状态机，完成不重跑，未知不冒充未执行，续跑保留谱系 |
| 实验版本漂移 | 结束只检查 source/pipeline，未全面核对模型和额度；模型回执缺实际版本证据：[model.ts](../apps/medical-query/src/model.ts) | 执行、评分、知识及资源策略分别冻结；允许差异白名单和不具可比性的声明 |
| 观察不足以复原谱系 | publicTurn 省略部分身份；粗阶段缺 attempt/父产物/事件序列；流式正文先在内存：[application.ts](../apps/medical-query/src/application.ts)、[pipeline.ts](../apps/medical-query/src/pipeline.ts) | 事件与产物契约、完整性标记、部分流丢失边界、迟到事件处理，不编造未观测细节 |
| 结果发布缺唯一提交点 | data_result 可先被页面读取，但无显式发布版本 | 候选、验证、发布、答案完成的区别；发布原子绑定 SQL/结果/源/验证报告 |
| 诊断可能混淆起因与传播 | 缺机构键→计数放大→回答错误；跨进程错误目前偏重 message：[domain.ts](../apps/medical-query/src/domain.ts) | 稳定错误码、检查证据、根因候选与传播边、confirmed/suspected/unknown 的条件 |
| 评分扩展缺契约 | 新检查器缺输入时如何判分、异常怎样影响报告、人工裁定如何版本化仍待规定 | 输入/输出 schema、适用条件、依赖、证据要求、确定性和预算、兼容/重评规则 |
| 长期规模未验证 | stats/list 读取历史任务，提示词和目录体积随实验增加 | 索引、分页、产物引用、保留策略及代表规模下的性能验收 |

以上是源码和文档审查结论，不是已运行故障注入后的实测结果。

运行中的并发、期限及调用次数上限仍为必要控制，不因费用仅提示就允许无限调用。取消、超时、预算耗尽等实际任务结果保留在评分分母。性能报告继续区分排队、执行和混合负载，但不自行新增用户没有选择的性能发布门槛。

## RAG 与开源方案的进一步核查

当前 L0 是全 47 项目录识别后确定性展开，facts 才输入完整物理目录。原指标目录共 15 条别名，没有自然口语召回对照证据，不能从 106 张表推出必须引入向量库。正式阻断涉及绑定、引擎或规则缺口，找到文本片段不等于已补齐这些条件。

WrenAI 当前已转向 CLI/MDL，旧 Docker 产品保留在 legacy/v1。可借鉴权威语义资料与可重建索引分离；其默认 grep 是示例 recall，schema fetch 需要 memory 扩展，不能照搬旧 Qdrant 架构描述。[当前架构](https://github.com/Canner/WrenAI/blob/055830d786dbf9d2905e0f1095f18e889222a530/README.md)、[memory 契约](https://github.com/Canner/WrenAI/blob/055830d786dbf9d2905e0f1095f18e889222a530/docs/core/concepts/memory_system.md)。核查版本为 0.16.0、Apache-2.0；整套 Python/语义引擎及可选向量依赖的成本高于单独候选检索。

Langfuse 可接受现有 Pi 的 OTel 追踪和实验评分，包含 retriever/tool/generation/evaluator 类型，不必再执行一个 Agent。其自托管还需要 PostgreSQL、ClickHouse、Redis、对象存储和 worker，不能描述为 SQLite 插件。[观察类型](https://langfuse.com/docs/observability/features/observation-types)、[实验接入](https://langfuse.com/docs/evaluation/experiments/experiments-via-opentelemetry)、[部署依赖](https://github.com/langfuse/langfuse/blob/d07952ca9da9827ce2ea2c060d08027faacd8545/docker-compose.yml)。核查发布 v4.63.0；核心 MIT，企业目录另有许可。是否作为外部查看器尚未定案，不能替代本项目完整性台账。

Promptfoo 提供已有的实验查看、OTel 关联、续跑和限流方法。[恢复约定](https://www.promptfoo.dev/docs/usage/command-line/)会复用原运行选项并跳过已完成项；[限流文档](https://www.promptfoo.dev/docs/configuration/rate-limits/)区分并发与速率退避；[追踪文档](https://www.promptfoo.dev/docs/tracing/)将结果行关联 trace。[缓存说明](https://www.promptfoo.dev/docs/configuration/caching/)提示重复实验可能重用缓存，因此独立重复必须区分重新发请求与重放旧结果。其 MIT 仓库有测试和持续文档更新；本轮未运行上游测试，也未证明它可直接满足本项目跨实验全局配额与医疗评分契约。

所有方案均只核查，没有安装、上传业务资料或改变现有 Pi 执行链。Firecrawl 开发者索引用于优先发现，普通抓取此前额度耗尽，随后使用官方文档与 GitHub 补查。

## 技术收敛建议：完整产品契约

技术方案应按以下依赖组织，不能以删掉后面的能力代替完整验收。

| 模块 | 明确的产品及实现契约 |
| --- | --- |
| 实验控制 | 冻结 dataset/gold/源/规则/模型配置/代码/评分版本；持久化 case×variant×repeat×snapshot 槽位及发送前 requestId；工作台、API、CLI 同一状态机 |
| Pi 执行 | 单一控制进程持有 Durable Harness/Session；Pi 原生任务、事务提交、子任务 ownership、取消和检查能力负责生命周期；执行/评分进程不另开 Application 或自建模型额度 |
| 统一准入 | 所有实际模型请求经同一出口；运行任务、LLM 在途、供应商速率、实验/方案份额、排队及局部 CPU/SQL 额度分别计量；所有重试、修复和 judge 计入，不凭进程数扩容 |
| 恢复与收尾 | 对账早于恢复派发；未知外部调用不能因任务结束或租约过期就记作未执行；暂停停止新派发且允许在途收尾，取消传播并显示正在停止直到实际完成 |
| 证据与观察 | 稳定身份、父产物、事件顺序、已发/已响应/已落盘/未知状态；完整产物保留至手动删除；分页/索引/去重引用控制增长，容量不足背压，不自动删证据 |
| 检索与语义 | 审核后的结构化规则决定计算；文档提供出处与消歧证据；完整目录、词法及混合检索可比较，选择策略及索引版本可追踪，向量是否启用由实测决定 |
| 评分与扩展 | 每个检查器声明版本、输入与必需证据、适用条件、依赖、预算及错误语义；新增检查不能改写旧分数；人工裁定产生新版本，原始产物不变 |
| 对比与归因 | 机器核验允许变化项、缺失配对、缓存/负载和版本漂移；阶段修复、首次整题、策略配对、故障干预分别统计；未知与证据不足不伪造结论 |
| 工作台与发布 | 实验进度、暂停/取消/续跑、逐题 trace、方案差异、争议裁定和质量放行；主对话只发布验证通过的数值；质量决定发布，耗时费用提示 |

Pi 原生已有 `TaskDefinition` 版本及迁移、阶段 checkpoint、`runtime.commit`、子任务等待与取消、taskGraph/watch/inspect。必须遵守同一 Session 单 owner 的约束，不能将其当多个进程同时领取同一库的调度器；其 scheduler 也不自带业务要求的 5/10 数字上限。[Durable 规范](../packages/durable/docs/spec.md)、[scheduler](../packages/durable/src/harness/scheduler.ts)。

另有两项不可忽略的接入差异：`generation` 的 request 阶段恢复会重新发送模型请求；部分提交/等待操作会隐式恢复任务。因此启动对账不能先调用会恢复任务的操作，未知请求政策也不能只放在可继续执行的普通 hook 中。[generation 实现](../packages/durable/src/harness/generation.ts)。应用应保留 session 级外部调用账本，不能仅依赖终止后会退休的 task 文档；对提供商外部调用不承诺 exactly-once。

本地 worker 或 SDK 退出也不证明远端不再执行或计费。未知项不能因租约过期、取消或用户点击续跑而静默清零；若提供商没有查询/取消能力，必须把对账受限和额度阻断展示出来，明确的人工处置仍保留未知历史及可能费用。全局额度的保证范围是本产品受控出口，不能声称约束其他项目直接使用同一账号的流量。

“可归因”还需要修正 v2 的分母：修复若在中途介入，首次整题答案可能从未形成。阶段局部通过不等于首次整题通过。分别记录实际首次通过/失败、必要条件已证实违反、首次未观察；首次未知但触发修复的任务另计 V，不能仍写触发总数只有 T+U。最终正确率保留全部有效预定槽，首次可观察子集必须带覆盖率，整体修复收益另用 repair_off/on 配对估计。

若需要区分“定向修复有效”与“多一次调用有效”，对照必须包含相同预算的普通重试；冻结检查点的补跑分支也不能冒充当时真实发生的首次回答。已知错误注入证明机制行为，不能直接证明自然故障发生率或唯一根因。

## 已落实到 v3 的验收要求

完整设计需要逐项映射“产品行为→状态/数据契约→可观察证据→故障与负载测试→放行条件”，包括：多个实验/模型同时运行；资源饥饿和账号级额度；丢响应/进程死亡/续跑；源及模型漂移；未验证结果发布；评分器异常；检索缺失与错误口径；修复误触发及传播；对照负载污染；历史规模增长。

准确区分四种能力：原始产物重评、确定性 SQL 重放、重新运行随机模型、故障干预下的归因。原始产物在版本/证据兼容且采用确定性 scorer 时可精确复算分数；随机模型与故障干预不能承诺逐字相同或唯一根因。观测缺失必须显式暴露，不能补成零消耗或已成功。

本记录保存审查事实与已确认决定。Q10 确认后已完成[总设计](metric-evaluation-design.md)、[执行与共享资源契约](evaluation-runtime-contract.md)、[评分与发布契约](evaluation-scoring-contract.md)、[知识与观测契约](evaluation-knowledge-observability.md)，包含完整工作台、模块调用链及 A01–A25 验收矩阵。交叉审查收紧了未知续跑身份、检索配置发布门、资料撤回和迁移顺序；实际实现与故障/负载/真实模型验收仍待执行。
