# 评测执行与共享资源契约

更新：2026-10-21。状态：控制服务、共享资源、未知调用账本与恢复已实现；故障及负载的实际覆盖见[验收记录](evaluation-acceptance-report.md)，未覆盖场景继续保留。
本文落实[产品审查记录](evaluation-product-review.md)的九项决定，与[评测方案](metric-evaluation-design.md)、[诊断修复设计](diagnosis-repair-design.md)共同使用。本文为目标契约；实际配置和 API 用法见[应用说明](../apps/medical-query/README.md)，不能将契约条目自动视为已通过测试。

## 1. 保证范围与不变量

- 部署范围为单机多进程；工作台、API、CLI 使用同一实验服务和持久化记录，不各自执行一套实验。
- 默认全局模型在途额度为 5，可配置范围为 1–10；增加模型、实验、方案或 worker 不增加额度。
- 在线请求优先，评测有最低份额，实验之间公平；空闲额度可以借用，在途请求不能被抢占。
- 确定性工作可以自动恢复；可能已经发送但结果未知的模型调用必须先对账，再由用户显式续跑。
- 已知终态和评分不可被重跑覆盖；全部完整产物保留至手动删除，容量不足采取背压。
- 质量决定发布，耗时和费用只作提示；运行期限、调用次数、资源上限仍然是必要执行约束。
- 不承诺供应商 API 的 exactly-once，不把本地 SDK 返回、进程退出或租约到期解释为远端已停止。

## 2. 单机拓扑与唯一所有者

```text
工作台 / API 客户端 / CLI
          ↓ 同一控制接口
协调进程：实验控制 + 唯一 Pi Harness/Session + 资源账本 + 模型出口
          ↓ 持久化派发、带身份的本地 IPC
执行进程：只读 SQL / 纯计算 / 评分；不持有独立模型额度
          ↓ 返回产物引用和检查结果
协调进程：校验身份 → 提交状态/证据 → 更新资源 → 发布进度
```

协调进程是实验状态、资源许可、调用记录和 Pi Session 的唯一写入权威。执行进程不得自行 `Application.open()`、打开同一 Session 或绕过模型出口。
模型出口放在协调进程内，复用 Pi AI 与现有 ModelGateway；执行进程需要模型时提交调用意图，由协调进程准入和发送，不把供应商凭据分发给 worker。
Pi SQLite 存储负责持久化，但 WAL 和 `BEGIN IMMEDIATE` 不等于跨进程任务领取、租约或全局限流；不让多个 Harness 竞争同一存储库。[存储实现](../packages/durable/src/storage/sqlite/node.ts)
启动对规范化后的运行目录取得唯一进程锁，并校验进程实例身份；锁中记录 PID、启动时间和实例随机标识，不能只判断 PID 是否存在。
协调器身份与锁范围由安装级配置固定，不能按实验或 `dataDir` 派生。CLI、独立评测模式及多个实验库均连接同一出口；只有不调用外部模型的离线测试可独立运行。
旧协调进程仍存活或无法确认已退出时，新进程拒绝接管；确认旧进程退出后才能建立新的 `coordinator_epoch`。这仍不证明旧进程发出的远端调用已经结束。
每个 worker 注册唯一 `worker_instance_id`，每次派发绑定 `execution_id / operation_id / dispatch_revision / coordinator_epoch`；PID 和工作进程编号不能替代实例身份。
心跳超时只将 worker 标为可疑；先停止向它派发，确认退出后才能替换。心跳超时本身不能清除模型占用或触发外部调用重放。
迟到结果必须经过身份和状态校验：旧派发不能更新当前执行、分数或发布结果；其有效回执可以作为原调用的对账证据单独保存，不能一律丢弃。

## 3. 复用 Pi 的方式与限制

| Pi 原生能力 | 本产品复用方式 | 必须防止的误用 |
| --- | --- | --- |
| `TaskDefinition`、版本、迁移、阶段 checkpoint | 实验控制任务拥有槽位执行子任务，保存明确阶段及输入快照 | 迁移不能悄悄改变冻结规则或旧分数 |
| `runtime.commit` 与持久化文档 | 原子提交任务状态、子任务创建和证据引用 | 供应商调用不在 Session 事务内，提交不保证远端恰好执行一次 |
| 子任务 ownership、等待、`abortTask` | 传播取消标记，再单独确认本地任务树终态 | 实验子任务不能使用脱离普通取消树的 background ownership |
| `inspect`、快照、`taskGraph`、watch | 启动对账、状态读取、进度订阅 | 不能把只读观察替换成会恢复执行的等待或提交操作 |
| `resume`、提交、等待 API | 对账及版本校验通过后才允许调度 | 一些提交/等待操作隐式启用 scheduler，必须统一经过恢复门 |
| 原生 generation 与 Models 注入点 | 经资源和证据适配后复用模型阶段，不引入另一 Agent 运行器 | request checkpoint 恢复会再次发请求；未知调用不可直接交给它重放 |

依据：[任务类型](../packages/durable/src/types.ts)、[Harness API](../packages/durable/src/harness/types.ts)、[generation](../packages/durable/src/harness/generation.ts)、[运行规范](../packages/durable/docs/spec.md)。
原生 scheduler 会处理可运行任务，但不提供本产品的 5/10 上限、在线最低份额或实验公平性；准入由协调进程集中执行。[scheduler](../packages/durable/src/harness/scheduler.ts)
原生普通 hook 的异常不宜充当强制阻断门；准入、取消和未知状态检查必须放在实际受控模型发送入口，覆盖 generation、compaction、judge 和 embedding。
原生 generation 对 `length` 的处理不等于业务 JSON 已完整；现有结构校验与截断诊断必须保留。SDK、generation 和业务层重试必须选定一个实际重试所有者，避免乘法重试。
任务级文档可能随任务终止退休；调用账本、实验、槽位、发布记录和完整产物索引使用 session 级持久记录或受控业务存储，不能仅依赖 task 文档。
`abortTask` 持久化取消标记并等待当前调用收尾，不保证整个所属任务树已经终态；随后经恢复门检查再用 `waitForTask` 等确认本地终态。Session 失败也需单独显示，不能当作取消完成。
任务终态及 `close()` 等待本地处理器退出不等于远端取消确认。拒绝响应取消的执行进程由协调进程终止，其外部调用仍按未知流程处理。
当前应用使用自定义 Durable 任务与 ModelGateway。原生 generation 的接入必须先通过同一资源、重放、回执和 trace 契约测试；本文不声称现代码已完成这些适配。

## 4. 冻结身份、状态和评分归属

实验创建时冻结公开问题集、私有 gold、源数据、规则、文档/索引、代码/流水线、模型配置、评分器、修复策略及资源策略的版本或内容哈希。
`slot = (case_id, variant_id, repeat_index, snapshot_id)` 在实验内固定；同时保存 `experiment_id、slot_id、execution_id、turn_id、request_id、attempt_id`，不能只靠题目文字关联结果。
每个槽位有唯一原始执行。修复是这次执行中的有界阶段尝试；终态失败题的重新运行必须派生新运行或实验，并引用原槽位，不覆盖原记录。
工作台操作、API 和 CLI 使用相同控制命令、幂等键及预期版本；重复提交返回同一记录，幂等键对应不同内容返回冲突。

| 层级 | 状态契约 | 关键含义 |
| --- | --- | --- |
| 计划准入 | `draft / validated / frozen` | 草稿校验不派发；冻结身份、槽位和版本后才进入执行控制；冻结后修改须派生 |
| 实验控制 | `running / pausing / paused / cancelling / cancelled` | 用户意图与执行结果分开；完成后停止派发 |
| 实验汇总 | `queued / running / completed / incomplete`，另带 `reconciliation_required` | 所有预定槽都有可解释结果才算完成；需要对账可与暂停并存 |
| 槽位原始执行 | `planned / queued / running / waiting_for_user / succeeded / blocked / failed / cancelled / interrupted / reconciliation_required` | `blocked` 是业务结果，不等于错误，也不自动等于评测通过 |
| 阶段尝试 | `scheduled / running / succeeded / failed / cancelled / unknown` | 同一阶段修复新增 attempt，保留前一尝试的输入、错误和检查结果 |
| 外部操作 | `prepared / dispatching / in_flight / succeeded / failed / not_sent / unknown` | `unknown` 表示无法确定远端是否执行或结束，绝非未调用 |

取消请求另存 `cancel_requested_at`，不把 `cancel_requested` 直接当作远端操作终态。操作处置另存证据、操作者及 `reservation_disposition`，保留原观察事实。
实验取消或中断后可以形成不完整报告；取消、超时、未知、缺产物和未完成槽位均保留在相应分母，不能仅对成功返回项计分。
同一次请求的网络重试只重取原记录。确定性恢复沿用原执行身份；未知调用后的显式续跑生成关联的新执行记录，报告标注恢复来源与原未知尝试。
续跑成功不能把原槽位改成“一次即成功”；原报告保留未知或中断事实，新运行独立评分。严格配对对照不能删除旧尝试、可能费用或资源污染再宣称等价。
多轮追问、重启和同一执行的阶段恢复不得重置 turn 级调用/修复预算；用户明确创建的新运行可使用新预算，但累计消耗及谱系仍可查。

## 5. 发送前意图、回执与事件持久化

1. 在接收实验创建时持久化全部槽位与预定 `request_id`；客户端重启后按身份查询，不凭超时新建一题。
2. 发送前事务写入 `operation_id`、请求哈希、父 attempt、模型/账号范围、资源及调用预算预留和取消检查结果，状态为 `prepared`；取得发送权后将调用预算转为已消耗，不能在恢复时再扣一遍。
3. 模型出口领取发送权，持久化 `dispatching` 后才能访问供应商；此后失联按“可能发送”处理，即使没有首 token。
4. 收到远端请求 ID、响应头、首事件和结束事件即按序保存；未知字段记 `null` 并说明原因，不填零或推断实际模型版本。
5. 完整响应、用量、产物校验和操作终态先持久化，再释放相应额度并推进任务；跨产物文件与数据库用不可变文件及校验和引用提交，孤立文件不当作完成。
6. 返回给工作台的事件带单调序号与持久游标；断线按游标补读，不能由页面拼接状态来决定执行或评分。

只有能证明发送权未授予的 `prepared` 操作可自动标记 `not_sent` 并释放资源及调用预算预留，不计作已发请求。写了 `dispatching` 后，没有响应不等于没有执行，未知操作保留已消耗预算。
协调进程在“远端返回后、本地提交前”死亡仍会留下未知；仅靠客户端幂等键无法消除此窗口，除非供应商明确提供并验证了对应幂等能力。
本地同一 `operation_id` 的重复派发拒绝产生第二次发送；网络连接错误不自动换 ID 重试。已确认的暂态失败才按重试策略新增关联 attempt。
完整 trace 保存输入提示词、输出、工具结果、错误及父产物关系；部分流丢失时明确 `artifact_completeness=partial`，禁止补写成完整回答。产物完整性使用知识与观测契约中的 `complete/partial/unresolved/artifact_deleted`，报告有效性使用评分契约的 `valid/incomplete/invalid`，二者分开。
正式数值发布是独立原子提交，绑定源版本、SQL/计算产物、校验报告和发布版本；恢复或答案修复不能重放已经发布的计算并覆盖它。

## 6. 未知调用的对账与人工处置

未知操作继续占用“可能在途”额度，同时立即显示发生时间、账号范围、最后已知阶段、资源占用、可能费用、对账能力和下一步；不得只显示永久旋转的运行状态。
有供应商查询/取消接口时，以已保存远端 ID 执行有界只读查询或明确取消；对账请求使用独立低额管理速率，不绕过账号 API 限制，也不产生新的模型生成。
没有查询能力、查询失败或超过人工处理提示期限时，将原因明确标为“需人工处置”；提示期限不是远端结束时间，不能因超时自动释放额度。
支持以下处置，全部记录操作者、时间、原因、证据和原状态；处置与“显式续跑”是两步操作，处置本身不发送新模型请求。

| 处置 | 需要的证据或确认 | 额度与后续行为 |
| --- | --- | --- |
| 补录完成回执 | 可对应 operation 的供应商回执、用量和结果；缺失正文仍标不完整 | 完成对账后释放，保留原观察与补录来源；缺证据不能评分成功 |
| 确认未接受或已终止 | 供应商可核实的状态或取消确认 | 释放额度；仍保留可能已发生的费用，不把“已终止”推成零消费 |
| 继续等待 | 用户选择保留未知占用，并可再次对账 | 额度继续占用，明确显示阻断多少容量，不承诺等待一定有结果 |
| 接受不确定性并释放本地预留 | 用户明确确认无法核实远端结束、可能仍执行/计费，并填写原因 | 释放本地预留，但操作仍为 unknown，记录人工处置；新调用须显式续跑 |

最后一种处置是可见的风险决策，不是系统自动推断：`capacity_assurance=degraded_unknown_remote`，持续展示未核实远端数量及潜在费用。
此时只能保证受控出口中新授权、未处置调用的本地并发上限；远端实际在途可能包含被人工释放的旧操作，不能承诺仍严格不超过 5/10。
没有可靠后续证据，不得仅凭时间流逝清除 unknown 或恢复严格保证；人工释放数量单独统计，不从未知总量删除。
严格资源对照将这类运行标为受未知远端影响，不当作洁净并发基线；正常业务能否续跑由显式处置决定，而非以永久隐形占位代替处理流程。
对账发现迟到成功可补全原操作；若已有新运行，两个结果都保存，旧结果不得覆盖新运行或重复发布。供应商不提供可核验身份时，只能保留不确定性。

## 7. 恢复、暂停与取消

启动顺序固定为：取得唯一所有权 → 只读检查持久任务/操作 → 验证冻结版本 → 对账/分类 → 恢复确定工作 → 显式批准未知续跑；不得先 `resume()` 再补账。
恢复门必须逐任务隔离：应用 Durable 任务为未知依赖保存明确的 `reconciliation_wait` 阶段，恢复其他确定任务不得推进它的生成、修复或评分。Pi 的全局 `resume()` 不是选择性恢复 API。
实际发送任务使用 `TaskOptions.abandonOnRestart` 的重启放弃语义，父任务以 `allSettled` 读取终态与外部账本后进入对账等待；“本地已放弃、外部未知”同时保留。原生 generation 的适配也必须满足这一点，不能让 request checkpoint 重入后靠抛错阻止发送，再被原生失败/重试路径改判。
已完成操作直接使用已持久化产物；确认未发送的工作重新排队；纯确定性计算可按原版本恢复；版本缺失或改变则停止并显示具体差异。
可能已经发送的模型操作不自动重试；待用户回答的任务保持待答，不模拟用户回复，也不抢占活跃任务/模型额度。
暂停停止新槽位派发，已派发执行允许在原预算内完成，包括其定向修复；工作台显示“暂停中”及仍在收尾的数量，收尾后变为“已暂停”。
本地活动执行归零即可显示已暂停；仍有未知外部操作时同时保留“需要对账”与其占用，不因远端状态无法核实而永久停留在没有解释的暂停中。
暂停不等于取消；等待用户回复的槽位保持待答，但暂停期间不因回复自动启动执行，回复内容可以保存为待恢复输入。
取消先持久化意图，立即禁止新模型调用、修复和子任务派发，再向本地执行树传播取消；队列任务可立即终止，在途任务显示“正在停止”。
本地执行已停止但远端状态未知时，实验可显示“已取消，仍有调用待对账”；不得显示全部远端请求已取消或最终费用为零。
客户端断线、CLI 退出和关闭页面只停止观察；取消必须通过显式控制命令。重复暂停/取消/续跑按命令 ID 幂等，过期版本返回冲突。
取消后到达的响应保存为原操作证据，不继续修复、发布答案或派发下一题；已经发布的结果保留其历史版本并标记后续控制状态。

## 8. 分层资源、在线优先与公平借用

| 资源层 | 计量对象 | 约束与释放条件 |
| --- | --- | --- |
| 活跃执行 | 实际占用执行流程的 turn/run | 待答、纯排队不占用；恢复和修复不重复申请一份 turn 配额 |
| 全局模型 | 所有受控在途与未处置 unknown 操作 | 默认 5、上限 10；按回执或明确处置释放，不能随 worker 租约释放 |
| 账号/供应商 | 实际共享账号资源范围 | 所有模型别名共用对应账号额度，另受全局上限约束 |
| 类别/实验/方案 | online、eval 及实验内部队列 | 类别最低份额；eval 内实验轮转，实验内方案/重复均衡 |
| 速率 | 已知 RPM、TPM 及供应商反馈 | 与并发独立配置；等待速率许可不占模型在途额度 |
| 本地执行 | SQL 子进程、CPU 评分任务和产物写入 | 有界 worker 与队列；不能用放大进程数突破模型或存储约束 |

准入同时检查上述约束，通过后原子预留；等待账号速率或模型额度的执行不持有不必要的 SQL/CPU 许可，避免互相占位。
类别调度使用带最低份额的工作守恒策略：存在合格 online 和 eval 时，两者各至少得到一个可用槽，其余容量按 online:eval=4:1 权重安排。
最低份额是持续竞争下的服务保证，不是永远空置的专用槽；对方空闲时可以借用。借用请求完成后，下一个许可优先归还有欠额的类别。
全局额度为 1 时不能承诺同时各占一槽，改用有界轮转：两类持续可运行时最多连续派发 4 个 online 后派发 1 个 eval；配置校验禁止声明两个同时保留槽。
eval 内先按实验公平轮转，再按方案及重复轮转；单一大实验、较快模型或重复补充队列不能持续挤掉其他实验。相同公平规则适用于模型出口，不能只在 turn 入口生效。
活跃执行入口同样执行类别最低份额与借用规则，不能让 eval 长期占满全部 run 名额，使在线请求根本到不了模型队列。待答释放 run 许可；已借用名额中的活动执行自然收尾后，下一份许可归还有欠额的类别。
公平承诺以“有合格请求且真实额度持续释放”为前提；账号受限、未知占满或本地存储阻断时显示原因，不用正常排队时间掩盖无法派发。
队列总量有界，并为在线保留准入空间；eval 填满自己的份额时只拒绝或暂停更多 eval 入队，不挤占在线保留区。
达到队列容量时返回结构化原因与重试建议；未接受请求不伪造成功记录，已接受请求必须可按原 requestId 查回。实验保留 planned 槽，不必把全部题立即塞入执行队列。
队列等待、模型执行、总 run 期限分别计时。超时生成对应诊断和原始结果，不从评分分母移除；超时后的远端不确定性仍进入对账。

## 9. 账号范围、速率与本地计算

每个模型配置引用非秘密的 `resource_scope_id`，由配置人员确认哪些凭据、端点和模型共享账号额度；凭据轮换和模型别名不能自动创建新额度池。
本产品保证范围仅涵盖这个协调出口。其他应用直接使用同一供应商账号的流量不可观测，必须声明外部共享或全部路由到同一受控出口，不能声称账号整体绝不超限。
RPM/TPM 仅按实际账号能力及供应商说明配置；未知时为 `null` 并显示未配置，不编造 DeepSeek 额度，也不把 `null` 解释成已验证无限制。
TPM 可用时按输入估算与输出预算预留，回执后按实际用量结算；未知用量保留估算和不确定标记。供应商 429/Retry-After 触发账号退避，不反复占用运行槽重试。
全局模型计数包括识别、生成、修复、摘要压缩、LLM judge、embedding 和实际重试；另按用途统计，区分产品执行与评分成本。纯确定性评分不消耗模型许可。
产品 turn 与评分器分别声明调用预算，judge 不挤占产品 turn 的 8 次预算，但有自己的有界预算并共用全局出口；报告分别列出产品与评分调用。
单次逻辑节点暂态重试、整 turn 定向修复和该执行总调用上限共同校验；换模型、转交 worker 或重启不重置预算，失败尝试也计入已发调用数。
SQL 使用只读连接、语句期限和结果规模上限；单独限制同时查询数。取消必须中止对应本地工作并确认退出，不能把“发送中止信号”直接当成已释放 CPU/SQL 槽。
主业务查询每 turn 默认最多 2 次实际执行尝试，暂态失败也计入；发布结果后禁止替代执行，规则仍阻断的正式 L0 查询次数为 0。评测器的独立 oracle 或冻结查询重放使用单独有界预算，不计入产品 SQL 次数，也不能回流给产品修答案。
CPU 评分和大结果处理使用有界工作进程，避免阻塞协调进程心跳与事件持久化；模型等待不应占住 CPU 执行许可。

## 10. 建议默认配置与校验

以下是设计建议默认，需实现校验与故障测试后生效；不是当前已支持的配置文件格式。

```yaml
global_model_limit: 5                 # 整个受控出口；允许 1–10
active_run_limit: 5                   # 活跃执行上限；允许 1–10
class_weights: { online: 4, eval: 1 }
minimum_share: { online: 1, eval: 1 }  # limit=1 时必须改用串行轮转规则
queue_limit: 100
online_queue_reserve: 20
eval_queue_limit: 80
per_experiment_dispatch_window: 10
cpu_workers: 2
sql_concurrency: 2
queue_timeout_seconds: 300
model_timeout_seconds: 120
run_timeout_seconds: 600
turn_model_call_limit: 8
turn_sql_execution_limit: 2          # 主业务查询；发布后不再执行替代查询
turn_repair_limit: 1                 # 允许 0–2；答案修复最多 1 次，计入总数
node_transient_retry_limit: 1
unknown_manual_attention_seconds: 300 # 提示人工处理，绝不代表自动释放
account_limits: { rpm: null, tpm: null }
artifact_auto_delete: false
```

启动校验数值范围、正权重、队列保留空间、账号映射、SQL/CPU 能力及调用预算；`eval_queue_limit ≤ queue_limit - online_queue_reserve`，派发窗口不得突破全局队列。
动态降低额度时不抢占既有请求，只阻止新增，显示当前超出新上限的存量；提高额度仍不得超过 10，变更产生策略版本并记录生效时刻。
实验执行使用冻结策略；在线策略变更不能静默改变已运行实验。若共享环境策略必须改变，暂停相关实验并记录漂移，显式派生新运行后继续比较。
每个评分器和索引构建任务也必须声明自己的调用、CPU/SQL、输出规模与期限预算；不允许因不属于产品 turn 就无限调用。等待用户的时间单独记录，不计入活跃运行段期限；恢复后仍沿用累计调用/修复预算，运行段身份与耗时可查。
收费单价未知时费用为 `null`，已知 token 仍保留；估算、实际及可能额外费用分列。延迟和费用不单独阻断发布，但预算耗尽是实际失败结果。

## 11. 产物完整性与手动删除

提示词、完整响应、SQL、结果、诊断、评分、trace、源/规则版本及发布证据均按不可变产物保存，以内容哈希引用；列表分页，不每次遍历全部历史正文。
无自动过期或自动删除。磁盘达到预警/停止阈值时提示并停止接受新工作，为在途证据收尾保留空间；写入失败明确标记产物不完整，不能静默截断后继续评分通过。
手动删除需展示实验、对照、发布记录的依赖；活动或待对账操作先停止并完成明确处置，避免删除后失去唯一在途账本。删除后保留删除事实，相关报告显示证据已删除、不能再复核。
工作台可查看候选产物，主问答只展示通过验证的发布版本；完整性缺失、版本漂移或证据链断裂不能靠人工填一个成功状态越过质量门。

## 12. 定向故障与负载验收

以下是必须实现的验收场景，执行证据逐项登记在验收记录；每项均需记录操作账本、事件序列、资源峰值和最终产物，而非只看页面状态。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 3 个实验、2 个模型、多个 worker 同时运行 | 默认受控在途合计不超过 5；设为 10 时不超过 10；账号别名不扩容 |
| eval 饱和后持续在线请求进入 | 在线获得优先服务且有队列空间；eval 持续获得最低份额，实验之间不饥饿 |
| 在线借满/评测借满后另一类到达 | 已发请求不抢占；后续许可按欠额归还，等待原因和时间可见 |
| 供应商 429、速率许可耗尽、队列满 | 有界退避和明确背压；不反复派发、不占住其他账号可用额度 |
| 发送前死亡 / 接受后丢响应 / 回包后提交前死亡 | 分别判定可证明未发与未知；请求 ID 可查回，未知不自动重复调用 |
| worker 或协调进程死亡、旧实例迟到回包 | 唯一 owner 不重叠；新 epoch 拒绝旧写入，原回执可对账且不能覆盖新执行 |
| 同一 Session 含确定性待恢复任务与未知模型任务 | 前者自动恢复；后者进入对账等待，不重新发送、不自动失败/修复、不消耗新调用预算 |
| 取消、暂停、待答、重复控制命令 | 符合收尾和幂等语义；待答释放活跃额度，取消禁止新增修复和发布 |
| 未知占满及人工释放预留 | 明确显示阻断和处置选项；释放后保留 unknown、可能费用及容量保证降级 |
| 终态失败重跑、未知显式续跑 | 形成关联新运行；原分数和首次观察不改写，对照标记恢复与污染 |
| 版本漂移、产物写失败、磁盘不足 | 停止不安全恢复/新派发；证据不完整不能发布，不自动清理旧产物 |
| 1/5/10 并发与代表性历史规模 | 报告排队/执行/混合负载及公平性；耗时费用作提示，严重语义违规阻断放行 |

放行证据必须证明所有入口共用准入、未知不静默丢失、数值发布受验证控制、原始评分不可被重跑改写；不能以平均延迟较低代替这些证明。
