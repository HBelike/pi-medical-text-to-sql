# 模型计量与恢复验证

1. 目标：所有模型角色仍经过同一 Pi AI 网关和资源池；修复速率窗口在重启、延迟准备、不完整用量及网关错误时低估额度的问题。未修改 Pi 上游。
2. `model.ts` 按实际 system/user 文本 UTF-8 字节数加最大输出量保守预约 TPM；获得准入后准备账本，网络发送时记录时间，确定未发送的失败撤销预约。速率等待不占在途名额。
3. 尚未发送的预约不会因准备时间超过一分钟而过期；已发送项按发送时间进入一分钟窗口。重启优先使用持久回执 `sent_at`，其次派发时间，旧记录回退最后更新时间。
4. `model-usage.ts` 使用 Pi 原生 `onProviderStreamEvent` 观察归一化前的计量，原生流和正文解析保持由 Pi 承担。原始输入、输出、缓存及总数核验一致后结算；缺字段、非法或矛盾值保持 null 与预约，不把 SDK 补出的0当实测。
5. 明确的原始零用量合法；总输入已包含缓存，不重复相加。最后一个实际用量事件优先，文本/null帧不覆盖之前计量；未收到模型终态的用量不提升为最终回执。
6. 429 的 Retry-After 支持秒数和 HTTP 日期，不静默缩短为60秒；冷却期限写入操作回执，重启后恢复。408/5xx不证明远端终止，保持 unknown 与本地占位，禁止自动重发。
7. `test/model-rate-recovery.test.ts` 新增12项真实本机 HTTP/Pi/Durable 回归：实际 TPM 跨重启、缺失/部分/矛盾计量、明确0、两种429格式、实际发送晚于派发、准备跨分钟、确定未发送释放、408/502未知占位；全部通过。
8. 同次运行包括原模型6项及 `runtime-recovery-boundaries.test.ts` 四个实际SIGKILL断点，合计22/22、0跳过、4.26秒。四个断点分别为准备已提交、派发意图已提交、完整响应已收到但终态未提交、终态已提交；恢复不重发，迟到提交拒绝。
9. 用量观察器另有28/28原始事件与真实Pi钩子回归，由模块执行者实跑；与上述22项不混成一次调用。最终整合结果见[验收记录](evaluation-acceptance-report.md)。只用本机替身凭据，没有访问企业网关。
10. RPM/TPM 是配置账户的本地窗口控制，不宣称供应商跨机器配额协议或计费对账；成本未知仍为 null。真实136/21题发生于前一个执行版本，不能用这些修复覆盖其原始计量或成绩。
