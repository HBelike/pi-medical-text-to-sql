## 表的组织

26 张核心表保持原 DDL：机构、科室、患者、就诊、预约、住院、诊断、操作、临床事件、占床与开放床位、用药与 DDD、DRG、ICU、急诊抢救、人员、财务、资产负债余额、能耗、医保协议及管理证据等。

新增 10 个业务域，每域 8 表：

| 业务域 | 表示的事实与近义对象 |
| --- | --- |
| 机构空间 | 院区、楼栋、病区、护理单元、床资产、科室别名和历史、成本中心 |
| 患者背景 | 本地标识、人口学历史、医保登记、过敏和风险记录、同意、联系偏好、合并审核 |
| 门急诊流程 | 门诊排班、预约申请及状态、挂号凭据、分诊、排队号、实际接诊 |
| 住院床位流程 | 入院申请、分床、转科、出院医嘱、随访任务、家庭病床计划、护理班次、清洁任务 |
| 手术麻醉 | 手术申请、排程版本、手术间、麻醉评估与观察、安全核查、伤口评估、编码审核 |
| 护理院感 | 跌倒/压伤筛查、事件报告及复核、感染送检、标本、微生物结果、感染监测复核 |
| 药事供应 | 药品与批号、单位换算、医嘱及明细、发药、退药、库存移动 |
| 财务医保能源 | 会计期间、凭证与分录、资产台账、医保申报及状态、能源仪表与读数 |
| 人员重症急诊 | 人员档案、科室任职、培训与排班、ICU 转入申请及设备、急诊分诊和抢救医嘱 |
| 管理信息化目录 | 预算及调整、制度版本、质委会计划、信息系统模块及变更、DRG 编码提交、目录导入 |

这些表用业务关系连接，不通过空表或重复表凑数。必须区分“申请/计划”和“实际发生”：手术排程不等于完成操作、发药不等于实际消耗、医保申报不等于确认收入、床资产不等于每日开放床位、会议计划不等于评审通过。

完整表名、中文字段释义、行粒度、主键、复合外键及数据行数见 `table-catalog.json`，建表文件为 `schema.sql`。

## 合成事实与适用边界

- 固定种子 `20261016`，每机构默认 200 名批量患者，另保留原控制样本；批量患者在 2025/2026 年各有一次住院，门诊发生于住院前。固定业务时间锚点为 `2026-10-15T12:00:00+08:00`，不是当前机器时间。
- 机构内局部患者、就诊、住院等编号可重复；关联必须含 `institution_id`。同人多次就诊、一次住院多操作、多预约记录等用于区分统计粒度。
- 九月保留可手算样本：H001 完成普通门诊 7 人次、5 位患者；非家庭病床出院 7 人次；对应 3 条操作、2 次手术住院；期末资产 1,000 元、负债 300 元。它们是明确约定下的校验锚点，不是正式指标结果。
- 业务时间采用上海本地文本。病例事件不能早于入院或晚于出院；死亡出院无患者带药或后续患者随访。家庭病床原样例无院内到病区/手术/ICU事实。支撑转科遵循占床记录，ICU 观察事件不另行推定科室迁移。
- 缺叫诊、缺报到、未到病区、未出院、零等待、取消、爽约、空结果、冲销和跨期样本保留。没有执行的申报、检查、会议等字段保留 NULL，不填成已完成。
- DDD 的 g/mg 需要换算；SYN_DRUG_A 的 2025/2026 DDD 不同，DRG 的同码年度权重与费用不同。所有 `SYN_*` 目录、代码、参考值均为测试设计，不能冒充正式国家标准。
- 原六份知识文件按字节复制并记录哈希，所有待确认项保留。只在新库修正原局部样本 S004 的死亡后再次入院、S010 的成人新生儿标记，并按到病区时间重建占床事实；原夹具未改。

## 问题与标准答案

| 类别 | 数量 | 预期 |
| --- | ---: | --- |
| 正式指标识别与依赖匹配 | 47 | 正确指标、字段、关联、时间及具体缺口 |
| 要求正式计算的边界问题 | 47 | 保留阻断原因，不生成伪造指标数值 |
| 原始事实查询 | 30 | 按显式机构、时间、类型、粒度返回结果 |
| 显式合成计算 | 10 | 比率、时间差、DDD 换算、跨年增长、参考权重等测试数值 |
| 目录外 / 必须澄清 | 2 | 不乱套指标，不猜对象、科室或时间 |

40 道数值题中有 18 道多表题；另覆盖空集、零分母、缺失时间及不同中位数情况。示例为“九月普通门诊有多少人次/多少人”“九月出院对应多少条操作/多少次手术住院”“按发生时间对应版本换算非带药抗菌药 DDD”。问题逐条写明测试约定，不默认解决官方争议。

`questions.jsonl` 每行仅有 `id/source_id/question/as_of`，可作为产品问题输入。`evaluation/gold.jsonl` 包含独立 Python 答案、参考 SQL、所需表、规则、拆分和错误变形，只供外部评测器读取。每题先从原始行用 Python 计数、关联、Decimal 或时间运算，再与 SQL 结果比较；不调用被测模型或产品编译器生成答案。

按 20 个业务族固定拆分为开发 110 题、保留 26 题；同公式与近义题不跨两组。作者能够看到保留集，因此它不是独立第三方盲测。不能把这些题连同答案送给模型，再称为未见题评测。

五类错误变形：漏机构过滤、人数冒充人次、漏余额快照日期、连接漏机构键、固定错误 DDD 年度版本。生成时要求所有错误结果均能被独立答案识别。9 个手算锚点额外校验，避免 SQL 与 Python 同时误算而无对照。

## 调用链与接入

`npm run fixtures:l0-benchmark` → 原 L0 DDL → `l0_benchmark_core.py` → `l0_benchmark_support.py` → SQLite 完整性/外键/非空检查 → 只读 `l0_benchmark_questions.py` → 独立答案与 SQL 核验 → 导出结构、知识、问题、私有 gold 和清单。

从 `apps/medical-query` 目录执行：

```sh
npm run fixtures:l0-benchmark
```

默认目录已经生成，再执行会拒绝覆盖。需要新快照时：

```sh
npm run fixtures:l0-benchmark -- --output-dir .local/l0-benchmark-seed2 --seed 20261019 --patients-per-institution 200
```

只用 Python 标准库，未新增框架或依赖，未改 Pi 核心和模型并发。规模参数范围 8～10,000；小规模用于快速结构测试，大规模分布仍是合成设计，不承诺真实医院负载或临床分布。

`sources.fragment.json` 是符合现有读取契约的顶层数组，可按 ID 合并进来源清单，包含同一个数据库的两个逻辑入口：

| source_id | 用途 |
| --- | --- |
| `l0_benchmark` | 有 `knowledge_path`，沿现有 L0 识别/投影/匹配链路，正式计算保持阻断 |
| `l0_benchmark_facts` | 无 `knowledge_path`，走现有普通查询入口；用于显式原始事实题 |

本次未修改当前 `.local/sources.json` 或服务。不要用片段整体替换已有来源清单。题集每题已经指定入口；复杂合成计算虽有可执行参考 SQL，现有产品 DSL 不一定支持，本次没有新增算子，也没有将参考 SQL 送给产品执行。新题集格式与旧 `eval:linking` 的单文件格式不同，需要后续评测适配器按公共问题/私有 gold 分别读取，不能直接把 gold 当旧题集输入。

模型可见 `semantic.json` 保留业务语义；支撑表的测试角色和相关指标标签放在 `evaluation/table-roles.json`。知识目录中的合成枚举遵循现有 `global_rules[].field_values` 契约，保留整数/字符类型；完整生成统计和保留集说明只在包外层约定中。
